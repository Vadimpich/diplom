# AGENTS.md
## Правила работы субагентов в проекте

---

# 1. Источники истины (обязательно к соблюдению)

В проекте используются три ключевых документа, через которые синхронизируются все агенты.

## 1.1 docs/00_project.md
Главный документ проекта.

Содержит:
- полное ТЗ;
- архитектуру;
- требования;
- workflow;
- ограничения;
- принципы системы.

Правила:
- изменяется только пользователем вручную;
- агенты НЕ имеют права его редактировать;
- перед началом любой задачи агент обязан учитывать его содержимое.

---

## 1.2 docs/01_contract.md
Единый источник контрактов.

Содержит:
- HTTP API (эндпоинты, payload);
- структуры запросов и ответов;
- RabbitMQ сообщения;
- форматы данных между сервисами;
- ML input/output схемы;
- интеграционные контракты (например КЭСМИ).

Правила:
- при ЛЮБОМ изменении контрактов агент обязан обновить этот файл;
- нельзя менять контракт в коде, не обновив этот файл;
- другие агенты обязаны читать его перед реализацией.

---

## 1.3 docs/02_implementation.md
Текущий статус реализации.

Содержит:
- краткое описание реализованных фич;
- изменения по модулям;
- добавленные сервисы;
- важные архитектурные решения;
- текущую стадию разработки.

Правила:
- после выполнения задачи агент обязан добавить запись;
- запись должна быть краткой и по делу;
- не переписывать историю, только дополнять.

---

# 2. Общие правила разработки

## 2.1 Работа через документы
Субагенты НЕ синхронизируются напрямую.

Вся синхронизация происходит через:
- код;
- docs/01_contract.md;
- docs/02_implementation.md.

---

## 2.2 Запрет на silent changes
Запрещено:
- менять API без обновления docs/01_contract.md;
- менять payload очередей без фиксации;
- менять схемы данных без миграций и описания;
- менять статусы workflow без отражения в документации.

---

## 2.3 Минимальность изменений
- менять только то, что требуется задачей;
- не рефакторить “заодно”;
- не переписывать большие части системы без необходимости.

---

## 2.4 Идемпотентность
Обязательно учитывать для:
- публикации задач;
- обработки результатов;
- завершения обследований;
- интеграций.

---

## 2.5 Наблюдаемость
Любая критичная логика должна иметь:
- логирование;
- обработку ошибок;
- понятное поведение при сбоях.

---

## 2.6 Безопасность
- не хардкодить секреты;
- не делать внутренние сервисы публичными;
- не логировать чувствительные данные;
- не отдавать сырой stack trace наружу.

---

# 3. Роли субагентов

---

## 3.1 Frontend Agent

Зона ответственности:
- Next.js frontend;
- UI;
- формы;
- страницы;
- интеграция с API;
- отображение статусов.

Обязан:
- использовать только контракты из docs/01_contract.md;
- не придумывать новые API;
- корректно отображать backend статусы.

Запрещено:
- менять backend;
- менять контракты;
- реализовывать бизнес-логику анализа.

---

## 3.2 Core Backend Agent

Главный агент по логике системы.

Зона ответственности:
- Go backend;
- API;
- auth;
- PostgreSQL;
- workflow обследований;
- orchestration;
- RabbitMQ;
- S3;
- интеграция с ML и КЭСМИ.

Обязан:
- обновлять docs/01_contract.md при изменении API и событий;
- соблюдать статусную модель из 00_project.md;
- использовать PostgreSQL как source of truth;
- сохранять архитектурную целостность.

Запрещено:
- переносить ML-логику в core;
- передавать файлы через очередь;
- менять контракты без фиксации.

---

## 3.3 ML Backend Agent

Зона ответственности:
- Python ML сервисы;
- анализ речи;
- текст;
- акустика;
- паралингвистика;
- baseline.

Обязан:
- строго соблюдать входные/выходные схемы;
- фиксировать любые изменения форматов в docs/01_contract.md;
- делать сервисы независимыми друг от друга.

Запрещено:
- менять workflow core;
- напрямую менять БД core;
- ломать совместимость payload.

---

## 3.4 DevOps Agent

Зона ответственности:
- Docker;
- docker-compose;
- env конфигурация;
- CI/CD;
- запуск системы;
- инфраструктура.

Обязан:
- документировать env переменные;
- обеспечивать воспроизводимый запуск;
- не ломать существующие сервисы.

Запрещено:
- менять бизнес-логику;
- внедрять магические настройки без документации.

---

# 4. Обязательный порядок работы

Для любой задачи агент должен:

1. Изучить docs/00_project.md (если задача архитектурная или сложная);
2. Проверить docs/01_contract.md;
3. Выполнить изменения в своей зоне ответственности;
4. Обновить docs/01_contract.md (если затронуты контракты);
5. Добавить запись в docs/02_implementation.md.

---

# 5. Главный принцип

Система должна оставаться согласованной.

Если решение:
- ломает контракты,
- нарушает workflow,
- создаёт скрытые зависимости,
- или не зафиксировано в документации,

оно считается неправильным, даже если работает.
