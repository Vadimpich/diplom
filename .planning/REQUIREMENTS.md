# Requirements: Мультимодальная система оценки психоэмоционального состояния специалистов

**Defined:** 2026-03-20
**Core Value:** Система должна давать оператору надёжный, интерпретируемый и воспроизводимый результат обследования специалиста, основанный на полном мультимодальном анализе речевых ответов, а не на ручной субъективной оценке.

## v1 Requirements

### Access Control

- [ ] **ACCS-01**: Пользователь может получить access token по логину и паролю через защищённый auth flow
- [ ] **ACCS-02**: Пользователь может обновить access token через refresh flow без повторного ввода логина и пароля
- [ ] **ACCS-03**: Пользователь может завершить сессию через logout с отзывом refresh token
- [ ] **ACCS-04**: Backend ограничивает доступ к admin и operator возможностям по ролям на стороне сервера, а не только во frontend

### Examination Flow

- [ ] **EXAM-01**: Оператор может создать обследование для выбранного специалиста и опросника
- [ ] **EXAM-02**: Оператор может загружать отдельные аудиоответы с привязкой к обследованию, вопросу и специалисту
- [ ] **EXAM-03**: Оператор может завершить обследование, и backend идемпотентно переводит его в обработку только один раз
- [ ] **EXAM-04**: Система хранит и отображает историю обследований специалиста с актуальными статусами workflow

### Processing Pipeline

- [ ] **PIPE-01**: Core backend публикует задачи анализа в RabbitMQ для каналов `text`, `acoustic` и `paralinguistic` с версионируемым payload и ссылкой на аудио в S3
- [ ] **PIPE-02**: Каждый ML-сервис получает задачу, обрабатывает аудио независимо от других сервисов и возвращает унифицированный результат своего канала
- [ ] **PIPE-03**: Система ограничивает повторные попытки обработки и фиксирует временные и фатальные ошибки по каждому каналу
- [ ] **PIPE-04**: Если хотя бы один обязательный канал не завершился успешно после допустимых retry, обследование получает финальный error state

### Aggregation

- [ ] **AGGR-01**: Aggregator ожидает успешные результаты всех обязательных каналов перед формированием итогового профиля
- [ ] **AGGR-02**: Aggregator нормализует результаты каналов и сохраняет агрегированный, версионируемый профиль состояния обследования
- [ ] **AGGR-03**: Система сохраняет вклад каждого аналитического канала и интерпретируемое объяснение результата

### Baseline

- [ ] **BASE-01**: Baseline service рассчитывает отклонение обследования от общей нормы и индивидуальной нормы специалиста
- [ ] **BASE-02**: Baseline-профиль хранит дату актуализации, число учтённых обследований и версию алгоритма
- [ ] **BASE-03**: Алгоритм baseline устойчив к единичным аномальным обследованиям и не обновляет профиль бесконтрольно

### Decision Integration

- [ ] **KSMI-01**: Система передаёт итоговый нормализованный профиль обследования в КЭСМИ через изолированный integration layer
- [ ] **KSMI-02**: Интеграция с КЭСМИ идемпотентно обрабатывает временные сетевые ошибки, различает transport и business errors и сохраняет correlation ID
- [ ] **KSMI-03**: Оператор видит итоговую рекомендацию `допуск / риск / недопуск` вместе с причиной интеграционной ошибки, если внешний вызов не завершился успешно

### Results Experience

- [ ] **RSLT-01**: Оператор видит прогресс обработки обследования по каждому обязательному каналу
- [ ] **RSLT-02**: Оператор видит экран результата с итоговым решением, ключевыми показателями состояния, отклонением от baseline и вкладом каналов
- [ ] **RSLT-03**: Оператор может просматривать динамику показателей специалиста по истории обследований

### Audit and Observability

- [ ] **OBSV-01**: Система ведёт audit trail для входов, критичных административных действий, создания и завершения обследований, запуска обработки и получения результата
- [ ] **OBSV-02**: Все сервисы публикуют health/readiness endpoints и базовые метрики по HTTP, БД, очередям, S3 и ошибкам
- [ ] **OBSV-03**: Логи и трассировки коррелируются по request ID или trace ID для воспроизведения маршрута обработки обследования

### Quality and Contracts

- [ ] **QUAL-01**: Все межсервисные и HTTP-контракты системы зафиксированы и версионируются в `docs/01_contract.md`
- [ ] **QUAL-02**: Критичные части workflow покрыты тестами на уровне unit/integration/API, включая статусные переходы, идемпотентность и обработку ошибок
- [ ] **QUAL-03**: Локальный self-hosted запуск воспроизводим через контейнерный стек для frontend, core backend, PostgreSQL, RabbitMQ, S3 и последующих аналитических сервисов

## v2 Requirements

### Administration

- **ADMN-01**: Администратор может управлять политикой TTL хранения аудиофайлов через UI и backend settings layer
- **ADMN-02**: Администратор может просматривать журнал аудита и техническую статистику без обращения к инфраструктурным системам напрямую

### Decision Support

- **DCSN-01**: Система показывает confidence score итогового решения, если этот показатель будет отдельно утверждён
- **DCSN-02**: Система поддерживает расширение новыми аналитическими каналами без пересмотра базового orchestration flow

## Out of Scope

| Feature | Reason |
|---------|--------|
| Полностью автономное принятие решения без участия оператора | Противоречит целевому назначению системы как decision-support инструмента |
| Публичная регистрация и внешнее пользовательское самообслуживание | Система проектируется только для внутреннего контура организации |
| Передача аудиофайлов через очередь сообщений | Прямо запрещено архитектурными ограничениями |
| Сохранение полной транскрипции как долговременной бизнес-сущности | ТЗ требует хранить derived features и технические метаданные, а не постоянную текстовую расшифровку |
