- Для Phase 1 начата реализация wave 2: backend-router разделён на role-scoped группы `admin` и `operator/admin`, а frontend auth transport переведён на Next.js BFF endpoints `/api/auth/*`, где refresh-session хранится через `HttpOnly` cookie и больше не записывается напрямую через `document.cookie`.
- Protected frontend layouts и `RouteGuard` переведены на BFF-backed session bootstrap через `/api/auth/session`: доступ в `/admin/*` и `/operator/*` больше не опирается на access-token cookie как на источник истины, а root/login redirects синхронизированы с refresh-session presence и ответом session endpoint.
- В intake-контуре ответы начали связываться не только с обследованием, но и с snapshot-вопросом/специалистом: `POST /answers` теперь требует `examination_question_id` и `specialist_id`, а backend валидирует принадлежность snapshot-вопроса конкретному обследованию и отклоняет дубликаты по одному вопросу.
- Завершение обследования переведено на transactional finish fence: `POST /examinations/{id}/finish` требует полноты ответов по `examination_questions`, идемпотентно удерживает единственный processing launch и оставляет `GET /specialists/{id}/examinations` авторитетным источником workflow-статусов.
- Specialist history UI на `/operator/specialists/[id]` теперь показывает статусы `created`, `collecting_answers`, `ready_for_processing` и timestamps напрямую из backend API, без вычисления workflow из локального состояния браузера.

- В `core-backend/internal/processing/publisher.go` добавлен фоновый outbox relay на `amqp091-go`: он объявляет RabbitMQ 3.13-совместимую topology с quorum queues, `processing.commands.dlx` и явным `x-delivery-limit`, публикует команды только после publisher confirm и пишет успешные/ошибочные попытки обратно в PostgreSQL для безопасного retry.
- Подключён route `GET /examinations/{id}/processing-status`: при наличии processing service backend собирает channel runtime state из PostgreSQL, а router/test fallback больше не падает на отсутствующем handler wiring.
- Core backend замкнул обратный async-контур: `internal/processing/results_consumer.go` читает unified queue `qq.processing.results`, а `internal/channelresults/service.go` сохраняет `channel_results`, переводит `examination_channel_runs` в `succeeded/retry_scheduled/failed_fatal/exhausted` и помечает обследование `failed` при исчерпании обязательного канала.
- Проекция `GET /examinations/{id}/processing-status` усилена backend-authoritative логикой: endpoint теперь отдаёт `409`, если обследование ещё не вошло в processing pipeline, и вычисляет `started_at`, `failed_at` и terminal-состояние только из PostgreSQL channel-run данных, без опоры на broker management state.
- Phase 2 закрыт reproducibility-обвязкой: локальный compose stack теперь поднимает frontend, core backend, PostgreSQL, RabbitMQ, MinIO и `text/acoustic/paralinguistic` stub workers как один проверяемый runtime; core backend использует явный `RABBITMQ_URL`, worker-очереди объявляются с теми же quorum/DLX retry аргументами, а runbook/validation зафиксировали команды smoke-проверки и operator-facing `processing-status` progress polling для shipped transactional outbox и channel queues pipeline.
